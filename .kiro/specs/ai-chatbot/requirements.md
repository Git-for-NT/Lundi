# Requirements Document

## Introduction

A full-stack AI chatbot application built as a learning project for an experienced software engineer exploring AI development. The system consists of a React + TypeScript frontend (Vite, port 5173) and a Node.js + Express + TypeScript backend (port 3001). The backend proxies user messages to the OpenAI Chat Completions API (gpt-3.5-turbo), maintains per-session conversation history in server memory, and returns complete responses to the client. The project is structured as a monorepo with separate `client/` and `server/` packages, prioritises readability, and ships with thorough explanatory comments and a production-quality code structure.

---

## Glossary

- **Chatbot**: The full-stack application described in this document.
- **Client**: The React + TypeScript + Vite frontend application located in `client/`.
- **Server**: The Node.js + Express + TypeScript backend application located in `server/`.
- **Session**: A browser session identified by a UUID stored in the browser's `sessionStorage`. Each session maps to an independent conversation history on the Server.
- **Session ID**: A UUID v4 string generated by the Client on first load and sent with every message request via the `X-Session-ID` HTTP header.
- **Conversation History**: An ordered list of OpenAI-format message objects (`{ role, content }`) stored in a server-side `Map` keyed by Session ID. History is lost when the Server restarts.
- **Message**: A single user or assistant turn in the conversation, conforming to the OpenAI `ChatCompletionMessageParam` type.
- **OpenAI API**: The external OpenAI Chat Completions API consumed by the Server.
- **Model**: The OpenAI language model used for completions, configured via the `OPENAI_MODEL` environment variable (default `gpt-3.5-turbo`).
- **API Key**: The OpenAI secret key stored in the `OPENAI_API_KEY` environment variable on the Server.
- **Monorepo**: The single repository containing both `client/` and `server/` packages, each with their own `package.json`.
- **CORS**: Cross-Origin Resource Sharing — HTTP headers that allow the Client (`:5173`) to call the Server (`:3001`) during development.
- **ESLint / Prettier**: Linting and formatting tools configured in both packages.

## Requirements

### Requirement 1: Monorepo Project Structure

**User Story:** As a developer learning AI development, I want a well-organised monorepo so that I can navigate and understand the full-stack codebase easily.

#### Acceptance Criteria

1. THE Monorepo SHALL contain a root `package.json` with `scripts` that start both the Client and Server concurrently for local development.
2. THE Monorepo SHALL contain a `client/` directory structured as a Vite + React + TypeScript project with its own `package.json`, `tsconfig.json`, ESLint config, and Prettier config.
3. THE Monorepo SHALL contain a `server/` directory structured as a Node.js + Express + TypeScript project with its own `package.json`, `tsconfig.json`, ESLint config, and Prettier config.
4. THE Monorepo SHALL contain a root `README.md` that documents project purpose, prerequisites, installation steps, environment variable setup, development commands, project structure, architecture decisions, request flow, and suggested learning extensions.
5. THE Client SHALL be configured to run on port `5173` via Vite's `server.port` configuration.
6. THE Server SHALL be configured to listen on port `3001`.

---

### Requirement 2: Server Environment Configuration

**User Story:** As a developer, I want environment variables to configure sensitive and environment-specific values so that secrets are never committed to source control.

#### Acceptance Criteria

1. THE Server SHALL load environment variables from a `.env` file in the `server/` directory using `dotenv`.
2. THE Server SHALL require the `OPENAI_API_KEY` environment variable and SHALL exit with a descriptive error message WHEN the variable is absent or empty at startup.
3. THE Server SHALL read the `OPENAI_MODEL` environment variable and SHALL default to `gpt-3.5-turbo` WHEN the variable is absent.
4. THE Server SHALL read the `PORT` environment variable and SHALL default to `3001` WHEN the variable is absent.
5. THE Monorepo SHALL include a `server/.env.example` file listing all required and optional environment variables with explanatory comments and placeholder values.
6. THE Monorepo SHALL include a root `.gitignore` that excludes `.env` files, `node_modules/` directories, and compiled output directories.

---

### Requirement 3: Server API Endpoint

**User Story:** As a developer, I want a single REST endpoint for sending chat messages so that the Client has a clear, documented contract to code against.

#### Acceptance Criteria

1. THE Server SHALL expose a `POST /api/chat` endpoint that accepts a JSON request body containing a `message` string field.
2. WHEN the `POST /api/chat` endpoint receives a request, THE Server SHALL read the `X-Session-ID` header to identify the session.
3. IF the `message` field is absent or not a non-empty string, THEN THE Server SHALL respond with HTTP `400` and a JSON body `{ "error": "message is required and must be a non-empty string" }`.
4. IF the `X-Session-ID` header is absent or not a valid UUID v4 string, THEN THE Server SHALL respond with HTTP `400` and a JSON body `{ "error": "X-Session-ID header is required and must be a valid UUID v4" }`.
5. WHEN the `POST /api/chat` endpoint receives a valid request, THE Server SHALL append the user message to the session's Conversation History before calling the OpenAI API.
6. WHEN the OpenAI API returns a successful completion, THE Server SHALL append the assistant message to the session's Conversation History and respond with HTTP `200` and a JSON body `{ "reply": "<assistant message content>" }`.
7. IF the OpenAI API returns an error, THEN THE Server SHALL log the error details server-side and respond with HTTP `502` and a JSON body `{ "error": "Failed to get a response from the AI service" }`.
8. IF an unexpected server-side error occurs, THEN THE Server SHALL log the error and respond with HTTP `500` and a JSON body `{ "error": "An unexpected error occurred" }`.
9. THE Server SHALL expose a `GET /health` endpoint that returns HTTP `200` and a JSON body `{ "status": "ok" }` for liveness checks.

---

### Requirement 4: Server CORS Configuration

**User Story:** As a developer, I want CORS configured on the Server so that the Client running on a different port can make API calls during development without browser security errors.

#### Acceptance Criteria

1. THE Server SHALL apply the `cors` middleware and SHALL allow requests from the origin `http://localhost:5173`.
2. THE Server SHALL allow the `Content-Type` and `X-Session-ID` headers in CORS requests.
3. THE Server SHALL allow the `POST` and `GET` HTTP methods in CORS requests.

---

### Requirement 5: Server Conversation History Management

**User Story:** As a user, I want the chatbot to remember what I said earlier in the conversation so that I can have a coherent multi-turn dialogue.

#### Acceptance Criteria

1. THE Server SHALL maintain a `Map<string, Message[]>` in process memory that maps Session IDs to ordered Conversation History arrays.
2. WHEN a session sends its first message, THE Server SHALL initialise the Conversation History for that Session ID with a system prompt that configures the assistant's persona.
3. WHILE a session's Conversation History exists, THE Server SHALL pass the full history as the `messages` array in every OpenAI API call for that session.
4. THE Server SHALL store Conversation History exclusively in process memory, with no persistence to disk or any database.
5. WHEN the Server process restarts, THE Server SHALL start with an empty Conversation History Map, effectively resetting all sessions.

---

### Requirement 6: Client Session Management

**User Story:** As a user, I want my chat session to persist across page navigations within the same browser tab so that my conversation is not reset by accidental navigation.

#### Acceptance Criteria

1. THE Client SHALL generate a UUID v4 Session ID on first load WHEN no Session ID is found in `sessionStorage`.
2. THE Client SHALL persist the Session ID in `sessionStorage` under the key `chatSessionId`.
3. THE Client SHALL include the Session ID as the value of the `X-Session-ID` header in every `POST /api/chat` request.
4. WHEN the browser tab is closed and a new tab is opened, THE Client SHALL generate a new Session ID, starting a fresh conversation.

---

### Requirement 7: Client Chat Interface

**User Story:** As a user, I want a clean, functional chat UI so that I can type messages and read the conversation clearly.

#### Acceptance Criteria

1. THE Client SHALL render a scrollable message list that displays all user and assistant messages in the current session.
2. THE Client SHALL visually distinguish user messages from assistant messages (e.g., different alignment, background colour, or label).
3. THE Client SHALL render a text input field and a send button for composing and submitting messages.
4. WHEN the user presses the Enter key in the input field, THE Client SHALL submit the current message, matching the behaviour of clicking the send button.
5. WHEN a message is submitted, THE Client SHALL clear the input field immediately.
6. WHILE a request to `POST /api/chat` is in progress, THE Client SHALL display a loading indicator and SHALL disable the input field and send button to prevent duplicate submissions.
7. WHEN the message list grows beyond the visible area, THE Client SHALL automatically scroll to the most recent message.
8. WHEN the Server returns an error response or a network error occurs, THE Client SHALL display a human-readable error message within the chat interface without crashing the application.

---

### Requirement 8: Client API Integration

**User Story:** As a developer, I want the Client's API communication isolated in a dedicated module so that the HTTP layer is decoupled from the UI and easy to maintain.

#### Acceptance Criteria

1. THE Client SHALL contain a dedicated API module (e.g., `src/api/chat.ts`) that exports a typed function for calling `POST /api/chat`.
2. THE API module SHALL use the Fetch API to make HTTP requests and SHALL set the `Content-Type: application/json` and `X-Session-ID` headers on every request.
3. THE API module SHALL throw a typed error that includes the HTTP status code and error message WHEN the Server responds with a non-2xx status.
4. THE Client SHALL configure the Vite dev server proxy to forward `/api` requests to `http://localhost:3001` so that the API base URL is not hardcoded in the API module.

---

### Requirement 9: Code Quality and Explanatory Comments

**User Story:** As a developer learning AI development, I want every file thoroughly commented so that I understand the purpose, design decisions, request flow, and potential improvements for each piece of code.

#### Acceptance Criteria

1. THE Monorepo SHALL configure ESLint and Prettier in both `client/` and `server/` packages with rules appropriate for TypeScript projects.
2. EVERY source file SHALL include a top-of-file comment block describing: the file's purpose, where it fits in the overall architecture, and the request flow that passes through it.
3. EVERY non-trivial function or component SHALL include an inline comment explaining what it does, why it is implemented that way, and at least one common mistake to avoid or one possible improvement.
4. EVERY environment variable and configuration value SHALL be accompanied by an inline comment explaining its purpose and acceptable values.
5. THE Server's OpenAI integration code SHALL include comments explaining the `messages` array format, the role of the system prompt, and the trade-off between streaming and non-streaming responses.
6. THE Client's session management code SHALL include comments explaining why `sessionStorage` is used instead of `localStorage` and what happens when the Server restarts.
